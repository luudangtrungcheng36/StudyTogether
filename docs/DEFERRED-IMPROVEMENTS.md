## Identity creation under concurrent requests

- **Problem:** two executions can both observe that a Discord identity is absent before either commits. This is a possible race, not an observed production incident or proof that the current bot invokes the service concurrently.
- **Current demo behavior:** find an existing identity or create its user and identity together using ordinary service-level `@Transactional`. Reuse preserves profile/login data. A persistence failure rolls back the new user and identity. The transaction joins an existing caller transaction when present.
- **Consequence of deferral:** when the draft SQL is applied, unique `(provider, provider_subject)` prevents duplicate identities; a losing concurrent creation may fail instead of automatically returning the winner. There is no automatic retry/reread.
- **Revisit when:** concurrent callers for the same Discord account are observed or explicitly become part of the next scope, such as bot and OAuth creation running in parallel or multiple application instances.
- **Possible implementation:** let the failed creation transaction finish rolling back, then perform the reread in a separate transaction. Proxied transactional methods or `TransactionTemplate` are alternatives to discuss then; neither is required for the current demo flow.
- **Suggested study when relevant:** after normal identity creation/reuse/rollback is runnable, demonstrate two callers both observing an absent identity before either commits. Trace the uniqueness failure and rollback, then compare keeping the error with separate-transaction recovery. Codex should recommend whether the actual callers justify recovery; do not assume TransactionTemplate is mandatory or automatically add this experiment to production code.
- **Cost:** additional recovery branches, transaction boundaries, and concurrency tests. Independent transactions also change whether a caller's later rollback undoes account creation, so that behavior needs an explicit decision.
- **History:** the earlier `REQUIRES_NEW TransactionTemplate` recovery and concurrent-winner test were removed on 2026-10-31 under the user's demo-first direction. Their previous passing results describe the superseded implementation.

## Study events under concurrency or replay

- **Current demo behavior:** StudySessionService uses ordinary transactions for session/segment writes, checks for an existing open user session, and ignores older observations for the matched open session. Exact identity/guild/channel matching prevents an old-room leave from closing the new room. No retry, per-user lock, or replay history was added.
- **Consequence of deferral:** simultaneous starts can both pass the lookup; the Discord partial unique index rejects one. Simultaneous media changes may compete for the same open segment. A replayed join after closure can create historical overlap. These are conditional risks, not reproduced live incidents. WEB-wide SQL enforcement is also still pending.
- **Suggested investigation after the listener demo:** first study two starts for one existing user that both read no open session before either commits. Compare the current database rejection with serializing operations on the user's row. Recommend a short user-row lock if multiple concurrent callers are introduced, because it coordinates reads and writes across application instances; an in-memory lock only coordinates one process. Agree scope and reproduce the race in a test before adding the lock. Handling brand-new identity races remains the separate topic above.
- **Cost and trigger:** extra locking, ordering, and concurrency tests; revisit for observed concurrent events, multiple instances, or WEB study. Complete replay/recovery requires a separately agreed event/checkpoint policy and should not be claimed solved by a lock alone.

## Voice observation time delayed by synchronous persistence

- **Evidence, 2026-11-03:** DiscordVoiceListener captures Instant.now() before calling the transactional service synchronously. DiscordBotConfig does not configure an event executor. JDA 6.7.0 dispatches listeners on the calling thread by default. A slow service can therefore delay subsequent callbacks and their observation timestamps. This is a source-based risk, not a measured live incident. The same event's captured timestamp does not advance merely because its DB write finishes later.
- **Deferred reproduction idea:** callback A captures time and then spends three seconds in persistence; callback B is ready one second later but runs after A returns, so B's timestamp is approximately two seconds late. If revisited, use controlled blocking in an isolated test rather than adding sleeps or fault injection to application code.
- **Earlier measurement recommendation (now deferred):** measure listener/service processing time and reproduce callback blocking before changing execution. These measurements identify local processing delays; Discord Voice State has no documented join/leave occurrence timestamp, so they cannot establish exact end-to-end latency.
- **Decision history, 2026-11-03:** the user initially preferred measurement before improvements and considered roughly one to two seconds acceptable. The proposed experiment compared persisted duration with screen-recorded join/leave actions on the same clock, plus local processing measurements; this would give an approximate action reference, not Discord's transition timestamp. The user subsequently said to skip this topic as unnecessary. No measurements, telemetry or execution changes are currently requested. Gateway heartbeat ping remains a diagnostic signal, not an event-latency measurement or upper bound.
- **Proposed alternative if selected:** capture IDs, both media flags and observation time into the existing immutable command before enqueueing DB work; initially process commands in arrival order with one worker. This lets the receiving callback return promptly and preserves captured timestamps despite persistence backlog. Merely moving callbacks to an executor and capturing time after its queue does not solve observation-time delay.
- **Tradeoffs and limits:** an executor/queue adds lifecycle, backlog and failure-handling decisions; queued in-memory work is not durable. Parallel workers require a separate ordering/concurrency design. This reduces application-induced blocking but cannot remove Discord/network delay or reconstruct exact historical timestamps. Never subtract a fixed delay or half the Gateway ping as a claimed correction.
- **Status/trigger:** explicitly deferred by the user's later 2026-11-03 direction; no async execution, queue, telemetry or recovery behavior implemented. Revisit only if the user selects it again or a concrete incident warrants a new discussion. Current demo continues synchronously while acknowledging the observation-time limit. Voice State reference: https://docs.discord.com/developers/resources/voice#voice-state-object. JDA default event dispatch: https://docs.jda.wiki/net/dv8tion/jda/api/JDABuilder.html#setEventPool(java.util.concurrent.ExecutorService).

## Live leaderboard refresh — discussion only

- **User question, 2026-11-03:** whether study minutes should update the leaderboard while participants are still studying. This is a feature discussion, not approval to implement or change scoring rules.
- **Current draft:** API_SPEC.md section 9 excludes ongoing sessions (includesOngoing:false); leaderboard/read APIs are not implemented. Refreshing that draft endpoint alone would still show only completed time.
- **Recommendation for discussion:** first build the read API, then refresh it from the frontend approximately every 30 seconds. Calculate from completed history plus an explicitly provisional ongoing contribution if the user agrees to change eligibility. Do not write accumulated totals to every user row each second. Immediate server push can wait until the periodic version demonstrates an actual need.
- **Required policy before counting ongoing time:** confirm current Discord presence and stop provisional accrual when that presence is uncertain, rather than treating every ended_at:null row as proof of continuing presence. Bot disconnect/restart and reconciliation are not implemented yet. Agree how provisional time affects ranks and becomes finalized on leave before changing API/database/architecture drafts.
